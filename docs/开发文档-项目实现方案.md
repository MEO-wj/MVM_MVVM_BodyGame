## 2. 技术选型

### 2.1 架构：推荐 MVP（而非 MVVM）

先讲清两者原理，再给结论。

**MVP（Model-View-Presenter）**

```
        用户事件(点击/输入)            调用算法/读写数据
View ────────────────────▶ Presenter ────────────────────▶ Model
  ▲                            │                              │
  └──────── 更新界面(调View接口) ┘◀──────────── 返回结果 ────────┘
```

- **Model（模型层）**：数据结构 + 业务/算法逻辑。它**完全不知道** View 和 Presenter 的存在，是纯 Python 代码，可以脱离界面独立运行、独立测试。
- **View（视图层）**：只负责"画"和"收事件"，是**被动视图（Passive View）**——它自己不做任何业务判断，把用户操作原样转发给 Presenter；同时暴露一组更新接口（如 `show_result()`、`show_error()`）供 Presenter 调用。
- **Presenter（演示器）**：中间人/粘合层。它同时持有 View 和 Model 的引用（**通过接口引用，不是具体类**），事件来了调 Model，结果出来调 View 刷新。

**MVVM（Model-View-ViewModel）**

- ViewModel 持有"可观察的状态"，View 通过**数据绑定**自动同步状态变化。
- 问题：**MVVM 依赖数据绑定机制**。Web 端的 Vue.js 天生支持，但 Python 桌面 GUI（PySide6/Tkinter/Pygame）**没有原生数据绑定**，需要自己用信号槽模拟，写起来别扭、容易绑错。

**结论：纯 Python 技术栈（前后端都用 Python）→ 选 MVP，最自然、最符合要求文档的"建议"；若前端执意用 Vue.js（Web 方案）→ 前端天然 MVVM，但后端仍须 Python，且两边要用 HTTP/WebSocket 接口解耦，工程量更大。本文档以 **MVP + PySide6** 为主线。**

### 2.2 界面框架：PySide6

对比候选框架：

| 框架 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **PySide6 (Qt6)** | 控件丰富、**信号槽机制**天然契合 MVP、官方维护、界面专业 | 安装包大 | ✅ 推荐，通用 GUI 应用 |
| Tkinter | 标准库零依赖 | 界面简陋、复杂布局难写 | 简单工具 |
| Pygame | 游戏循环、帧渲染强 | 没有控件系统，表单类交互极难写 | 游戏/可视化 |
| DearPyGui | GPU 渲染、实时数据可视化好 | 生态较小 | 仪表盘类 |

**PySide6 的信号槽（Signal/Slot）机制原理**——这是 MVP 落地的关键，必须理解：

- 信号槽是**观察者模式**的工程化实现：对象 A 声明"信号"（事件），对象 B 把自己的方法（槽）连接到该信号；A 发射信号时，Qt 自动调用 B 的方法。
- 它让 **View 不需要直接调用 Presenter 的方法**，只需"发信号"；Presenter 在初始化时把信号连接到自己的槽。这样 View 甚至不需要知道 Presenter 是谁 → 解耦更彻底。
- 信号槽支持**跨线程排队**（Queued Connection），耗时算法放子线程跑，结果通过信号发回主线程刷新 UI，界面不会卡死。

## 4. 系统架构设计

### 4.1 分层与依赖方向

**核心设计原则：依赖只能自上而下指向抽象接口，绝不允许跨层直连。**

```
┌─────────────────────────────────────────────┐
│  main.py（组装层 / 依赖注入）                  │
│  创建具体 View、具体 Model、Presenter 并接线    │
└──────────┬──────────────────────┬───────────┘
           │                      │
┌──────────▼──────────┐  ┌────────▼─────────────────────┐
│  view/   (前端)      │  │  core/  (后端)                │
│  实现 IMainView 接口  │  │  实现 IImageService 接口       │
│  PySide6 控件+信号    │  │  图像算法、数据存取             │
└──────────┬──────────┘  └────────▲─────────────────────┘
           │ 信号(事件上行)         │
┌──────────▼──────────────────────┴─────────────────────┐
│              presenter/  (中间层，纯逻辑无 UI)           │
│         依赖抽象接口 IMainView / IImageService          │
└────────────────────────────────────────────────────────┘
                    contracts.py（接口 + 数据类的"契约"）
```

**为什么这样就能实现"替换前端/后端"？——依赖倒置原理（DIP）**

- Presenter 的代码里写的类型是 `IMainView` 和 `IImageService`（抽象接口），**不是** `MainWindow` 或 `OpenCVService`。
- 接口相当于"插座标准"：只要新组件实现同一插座，就能插进同一个 Presenter，Presenter 代码**一行不改**。
- 这正是要求文档说的："在不改变代码框架的前提下，单独替换前端或者后端"。

### 4.3 契约层设计（contracts.py，先写它再写一切）

这是整个架构的核心文件，**两个接口 + 数据类**：

```python
# contracts.py —— 前后端共同的"插座标准"
from abc import ABC, abstractmethod
from dataclasses import dataclass
from enum import Enum

# ---------- 数据类（Model 与 View 之间传递的"货物"）----------
@dataclass
class ImageInfo:
    width: int
    height: int
    path: str

class FilterType(Enum):
    GRAYSCALE = "grayscale"
    BLUR = "blur"
    EDGE = "edge"

# ---------- 后端接口：任何算法引擎都要实现它 ----------
class IImageService(ABC):
    @abstractmethod
    def load(self, path: str) -> ImageInfo: ...
    @abstractmethod
    def apply_filter(self, image: ImageInfo, f: FilterType, **params) -> ImageInfo: ...
    @abstractmethod
    def save(self, image: ImageInfo, path: str) -> None: ...

# ---------- 前端接口：任何界面都要实现它 ----------
class IMainView(ABC):
    # Presenter 调用这些方法 → 刷新界面
    @abstractmethod
    def show_image(self, info: ImageInfo) -> None: ...
    @abstractmethod
    def show_status(self, msg: str) -> None: ...
    @abstractmethod
    def show_error(self, msg: str) -> None: ...
    # View 实现后 → Presenter 订阅这些事件
    @abstractmethod
    def on_open_file(self, handler) -> None: ...      # 用户点了"打开"
    @abstractmethod
    def on_apply_filter(self, handler) -> None: ...   # 用户点了滤镜按钮
    @abstractmethod
    def on_save(self, handler) -> None: ...
```

### 4.4 各层实现要点

**Model 层（core/）—— 纯 Python，不 import 任何界面库**

```python
# core/image_service.py
import cv2
from contracts import IImageService, ImageInfo, FilterType
from core import filters

class OpenCVService(IImageService):
    """OpenCV 算法引擎。内部用 numpy 数组存图，对 View 完全透明。"""
    def load(self, path: str) -> ImageInfo:
        img = cv2.imread(path)
        if img is None:
            raise FileNotFoundError(path)
        # ... 存入内部缓存，返回 ImageInfo
    def apply_filter(self, image, f, **params):
        fn = filters.REGISTRY[f]          # 算法注册表：FilterType → 处理函数
        result = fn(self._cache[image], **params)
        # ... 返回新的 ImageInfo
```

**Presenter 层—— 一个类粘合两端，没有任何 Qt 代码**

```python
# presenter/main_presenter.py
from contracts import IMainView, IImageService, FilterType

class MainPresenter:
    def __init__(self, view: IMainView, service: IImageService):
        self._view = view          # 注意类型是接口，不是具体类！
        self._service = service
        self._current = None
        self._bind_events()        # 订阅 View 的用户事件
        self._view.show_status("就绪")

    def _bind_events(self):
        self._view.on_open_file(self._handle_open)
        self._view.on_apply_filter(self._handle_filter)
        self._view.on_save(self._handle_save)

    def _handle_filter(self, f: FilterType, **params):
        try:
            self._current = self._service.apply_filter(self._current, f, **params)
            self._view.show_image(self._current)      # 只调接口，不知具体界面
        except Exception as e:
            self._view.show_error(str(e))
```

**View 层（PySide6）—— 只"画"和"发事件"，零业务逻辑**

```python
# view/main_window.py
from PySide6.QtWidgets import QMainWindow, QLabel, QPushButton
from PySide6.QtCore import Signal
from contracts import IMainView

class MainWindow(QMainWindow, IMainView):
    # Qt 信号：View → Presenter 的事件通道
    file_opened = Signal(str)
    filter_requested = Signal(object, dict)

    def __init__(self):
        super().__init__()
        self._build_ui()                      # 摆控件、连布局
        self.open_btn.clicked.connect(
            self._pick_file)                  # 控件内部事件 → 自定义信号

    # ---- IMainView 接口实现：供 Presenter 调用 ----
    def show_image(self, info):
        self.image_label.setPixmap(self._to_pixmap(info))
    def show_status(self, msg):
        self.statusBar().showMessage(msg)

    # ---- 事件订阅点：供 Presenter 注册回调 ----
    def on_open_file(self, handler):
        self.file_opened.connect(handler)
```

**组装层 main.py —— 全项目唯一知道"具体类"的地方（依赖注入）**

```python
# main.py
import sys
from PySide6.QtWidgets import QApplication
from view.main_window import MainWindow
from core.image_service import OpenCVService
from presenter.main_presenter import MainPresenter

def main():
    app = QApplication(sys.argv)
    view = MainWindow()              # 想换 CLI 前端？换成 CliView() 即可
    service = OpenCVService()        # 想换 YOLO 后端？换成 YoloService() 即可
    MainPresenter(view, service)     # Presenter 一行不改
    view.show()
    sys.exit(app.exec())
```

## 9. 常见坑预警

1. **View 里偷偷写业务**：图省事在按钮回调里直接调 cv2 → 架构分直接没了。所有事件必须经 Presenter。
2. **Presenter 直接 import PySide6**：会让 CLI 替换失败。Presenter 是纯 Python。
3. **信号传自定义对象**：Qt 信号传 Python 对象用 `Signal(object)`，注意传拷贝而非可变共享引用，避免界面和算法层改同一份数据。
4. **UI 卡死**：算法在主线程跑 → 大图卡界面。用 QThread + 信号回传。
5. **报告贴大段代码**：要求明确不贴代码，只允许"小段关键代码"；架构图用 draw.io / PlantUML 画。
